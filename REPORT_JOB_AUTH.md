# Scheduled ReportJob authentication

ReportJob is a separate reporting credential, not a user JWT. General authentication, user accounts, signing secret and JWT lifetime are unchanged.

## Scope

Supply `Authorization: ReportJob <credential>` only to:

- GET `/api/reports/generate`, with an optional single `month=YYYY-MM` query parameter (defaults to the previous calendar month).
- GET `/reports/YYYY-MM`, as an ordinary document request without query parameters.
- GET `/api/reports?month=YYYY-MM`, with exactly one valid month.

No other query fields are accepted for machine requests. HEAD and other methods are rejected. Report history, PDF download APIs, costs, AI, EC2, EBS and conversation APIs do not accept ReportJob. Existing user Bearer/cookie requests retain their existing authorization and CSRF behavior.

Only the two report API wrappers and report page establish verified request-local context. Each context is bound to its selected month; report storage helpers reject other months or unrelated object keys. General JWT helpers and generic internal fetch never accept this context as a user session.

Credential verification compares fixed-size SHA-256 digests using timingSafeEqual. Missing, empty, malformed or mismatched credentials fail closed. Machine-service failures use generic responses; raw service/browser exceptions are not returned.

## Configuration, not performed in production

The local ignored `src/lib/config/index.ts` contains an empty `REPORT_JOB_TOKEN` export. It is intentionally disabled. An older configuration without this export also disables ReportJob without requiring changes to user authentication.

Provision a separate high-entropy credential through the existing ignored server configuration arrangement. The accepted format is 32–256 ASCII letters, digits, underscores or hyphens; a randomly generated 256-bit base64url value is appropriate. No production credential was generated by this implementation. Never reuse the user JWT signing secret. This TypeScript configuration is imported into the server build: provision or rotate it before rebuilding, then replace/restart all relevant application processes during a separately approved rollout. Editing the source file alone does not rotate a running compiled application.

The cron caller needs a protected copy and must supply it as a header, not a query string or cookie. Keep it out of command-line arguments and logs, and fail on non-success HTTP responses. No cron, wrapper, Nginx or production configuration changes were performed.

Production `NEXT_PUBLIC_BASE_URL` still needs to be the public HTTPS application origin at build/runtime. ReportJob forwarding allows HTTPS or HTTP loopback only, not remote cleartext HTTP. Preserve Authorization through Nginx. TLS trust and deployed proxy forwarding have not been tested by this local implementation.

## Existing rendering is preserved

Generation uses the existing JSON/S3 cache and PDF keys. Puppeteer uses the existing Next.js report page and existing marker/navigation checks. Only the exact main report document receives Authorization; assets, iframes and redirected requests receive no credential. The page makes one narrowly targeted server-side data request to `/api/reports` with redirect following disabled. The credential is not passed into React props, HTML, browser storage or client modules.

The `/reports/*` proxy does not verify credentials or introduce a general identity framework. It rejects machine HEAD/non-document/RSC/prefetch variants, because the Server Component cannot directly inspect the HTTP method, and marks machine document responses private/no-store. Ordinary user requests pass through unchanged. Server-side verification remains in the report module.

## Validation and residual risks

Focused tests use synthetic credentials and mock S3, cost, OpenAI and Puppeteer services. They exercise the complete endpoint → report generator → report page → server-side data fetch → PDF chain, invalid/unconfigured credentials, all unrelated API handlers, concurrent month isolation, user authentication/CSRF regression and failure redaction. The client dependency test prevents configuration/report authentication imports into client graphs.

A stolen ReportJob credential permits generating/retrieving reports for any valid month and can incur reporting-service costs. It grants no infrastructure-management API access. No expiry, role system, rate limit, separate listener or loopback-only access policy was introduced. Use HTTPS except for local loopback and protect the credential/configuration files. Production logging must not record Authorization headers. Existing Puppeteer sandbox flags and cached PDFs are unchanged.

A separately approved deployment must provision the credential, correct the public origin before building, preserve the report-page proxy and deploy matching page/server code, verify Nginx forwarding, and update the monthly root job. Until then, the existing unauthenticated job will be rejected after deployment.

Final local validation: lint, TypeScript, all five test suites (272 tests, including 75 ReportJob tests), and the standard production build passed. A scan of 48 production browser/public assets found no configured user credential values or synthetic ReportJob test credential. ReportJob remains unconfigured locally.
